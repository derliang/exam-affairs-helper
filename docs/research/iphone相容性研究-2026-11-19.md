# iPhone 相容性研究：為什麼考務小幫手在 iPhone 上無法使用

> 2026-11-19，純研究，未改任何程式。版本基準：`main` 0d50cf8（v1.26.6）。
> 證據等級：**已實測**＝在內建瀏覽器實際操作；**程式推論**＝讀程式碼推得；**無法驗證**＝需要真實 iPhone；**來源**＝網路文件。

## 一、結論（先看這段）

1. **根本原因只有一個：資料存放設計。** 這個 App 把「使用者選的資料夾」當資料庫用，靠 File System Access API 的 `showDirectoryPicker()` 讀寫（決定 D1，`docs/decisions.md:10`）。**iOS 上所有瀏覽器（Safari、iPhone 版 Chrome 也一樣，因為 iOS 一律用 WebKit）都沒有這個 API**（來源見第六節）。沒有它，App 就沒有地方存名單、教室、排座結果，等於整個無法使用。
2. **跟「檔案 app 能開檔」不是同一件事。** 手機的檔案 app 能讓網頁「選一個檔案」（單檔讀取），但**不能讓網頁「選一個資料夾並持續讀寫」**。App 要的是後者。
3. **第二個問題（實測發現）：不支援的瀏覽器上，畫面會誤導。** 點「將資料夾拖曳至此」那一大塊，會直接進入「選好資料夾了」的首次設定，但實際用的是示範用記憶體存放，**重新整理就全部消失**（見 3.2）。
4. 即使繞過存放問題，匯出的「PDF（新分頁列印頁）」與多檔下載在 iOS 上也很可能不順（程式推論，見 3.4）。版面本身在 375px 寬沒有橫向溢出（已實測首頁）。
5. **建議（詳見第五節）**：短期先做「iPhone 明確提示＋修掉誤導的拖曳區」（成本極小）；要真的在 iPhone 用，需新增第二種儲存後端（瀏覽器內建儲存＋備份檔匯出／匯入），是中型工程，且 iPhone 上整個排座流程是否值得（小螢幕編輯座位表）要先請使用者決定。

## 二、使用者疑問的白話回答

> 「iPhone 的檔案 app 就能開檔，為什麼這個 App 不行？」

把 App 的動作分成三段看：

| 段落 | iPhone 行不行 | 為什麼 |
|---|---|---|
| **匯入單一檔案**（學生名單 .xlsx、備份 .json） | 多半可以（程式推論，無法驗證） | 這是普通的「選檔案」按鈕（`<input type="file">`），iOS 會跳出檔案 app 讓你挑。 |
| **存檔／讀檔（App 自己的資料）** | **不行（根本原因）** | App 不是「開一個檔案」，而是「拿到整個資料夾的長期讀寫權」，自動存很多小檔（設定、各次考試）。iOS 的網頁沒有這種資料夾權限，Apple 也明確不支援。 |
| **匯出（下載 Word／xlsx／PDF）** | 部分可行，PDF 流程可疑 | 下載能走 iOS 的下載管理員存到檔案 app；但「開新視窗列印」與一次下載多個檔案，在 iOS 上很可能被擋或要逐一確認。 |

比喻：檔案 app 好比「你遞一份文件給網頁看」；而 App 需要的是「給我一個抽屜的鑰匙，我自己隨時開關存取」。iOS 只肯給前者。

## 三、原因清單（含證據）

### 3.1 【致命】資料夾授權是唯一的儲存方式（程式推論＋已實測）

- `src/data/fsRepository.ts:83-85`：`isFsAccessSupported()` 只檢查 `'showDirectoryPicker' in window`。
- `src/ui/App.tsx:48-50`：不支援就改用 `createMemoryRepository()`（只存在記憶體，`src/ui/repository.ts:63-79`），並在初始化頁提示。
- `src/ui/pages/Init.tsx:75`：「選擇資料夾」鈕 `disabled={busy || !p.fsSupported}`；`:82-84`：不支援時顯示紅色提示「目前瀏覽器無法儲存資料。請用 Chrome 開啟本網站。」
- `src/data/dirfs.ts:115`：寫檔用 `createWritable()`，也是 File System Access API。
- 記住上次資料夾用 IndexedDB 存「資料夾控制代碼」（`src/data/fsRepository.ts:19`），沒有資料夾就沒有用。
- **已實測**：在 375×812 手機模擬、並把 `showDirectoryPicker` 從 `window` 移除（模擬 iOS 沒有該 API）後重新載入程式：「選擇資料夾」鈕停用，畫面出現上述紅色提示，與程式讀到的一致。
  - 限制：這是桌面 Chromium 模擬，不是 iOS WebKit；只證明「沒有該 API 時 App 的行為」，不證明 iOS 的其他行為。

### 3.2 【誤導】不支援時，拖曳區仍可點，進入假的「已選好資料夾」（已實測）

- `Init.tsx:62-70`：整塊 `dropzone` 的 `onClick={pick}` 沒有被停用（只有下方按鈕停用）。
- 點下去 → `repo.chooseFolder()` 在記憶體實作回傳 `true`（`src/ui/repository.ts:69`）→ 進入「首次設定」，文字寫「選好資料夾了」。
- **已實測**：確實如此；之後所有輸入只活在這次分頁記憶體內，重新整理即消失。老師在 iPhone 上可能花時間輸入後才發現沒存。
- 這是**獨立的 bug**（不依賴要不要支援 iPhone），建議無論選哪個解法都先修。

### 3.3 匯入（讀檔）：多半可行，需實機確認

- 學生名單、考試名單：`<input type="file" accept=".xlsx" hidden>`（`src/ui/pages/RosterIO.tsx:88`、`src/ui/pages/Step2.tsx:128`），由按鈕 `input.current?.click()` 觸發；讀取用 `file.arrayBuffer()` 加 JSZip（`RosterIO.tsx:48`、`src/import/xlsx.ts:78`），不依賴 DOM 以外的新 API。
- 分科備份／定案座位：`accept=".json,application/json"`（`src/ui/ast/AstRelease.tsx:107`、`AstSchedule.tsx:121`）。
- **程式推論**：這些在 iOS 的檔案選擇器應可使用。**無法驗證**：`accept` 只寫副檔名 `.xlsx` 而沒有寫 MIME，iOS 對副檔名過濾的實際表現要在實機確認；若有問題可補 `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`。
- 唯一的缺口：**整份資料的備份還原**（`encode`／`decode` 在 `src/data/envelope.ts:27,35`）目前只看到匯出（`App.tsx:83-86` 下載備份 json），我沒有找到一般畫面上的「匯入整份備份」入口（只搜尋了 `src/ui` 的 tsx，不保證沒有）。若要做 iPhone 版，這是必要功能。

### 3.4 匯出（下載與列印）：可疑（程式推論，無法驗證）

- 單檔下載：`src/ui/download.ts:3-11` 用 `Blob` ＋ `a[download]` ＋ `click()`；`src/ui/pages/Step6.tsx:22-30` 同樣寫法。這是 iOS Safari 近年支援的做法，單檔應可存到「檔案 app → 下載項目」，但 iOS 會彈出確認視窗（行為屬我既有知識，未查來源，標為無法驗證）。
- 多檔下載：`Step6.tsx:35-40` `downloadMany()` 每檔間隔 600ms 連續觸發；程式註解已承認連 Chrome 都會擋（#203）。iOS Safari 對連續下載的處理更保守，**很可能要使用者逐一確認，或只存下第一個**（推論）。
- PDF／列印頁：`Step6.tsx:62-69` `openPrintPage()` 用 `window.open('', '_blank')` ＋ `document.write()`；而且是在 `await` 字型載入與 `runExport` **之後**才呼叫（`Step6.tsx:198-207`）。瀏覽器的彈出視窗規則看「是否仍在使用者點擊的同步堆疊內」，這裡已經非同步，iOS Safari 很可能擋下（推論）；就算開得成，iOS 沒有桌面那種「另存為 PDF」的列印對話框（要用分享→列印→縮放存成 PDF），與 D29「使用者選另存為 PDF」的流程不合。
- 字型：匯出時才抓 4.8MB 的 Noto Sans TC（`src/export/fontLoader.ts`，字型資料夾共 6.5MB），在手機網路與記憶體上偏重；Word 檔嵌字型（`docxRender.ts`）理論上與平台無關。

### 3.5 JS／CSS 新功能：多數 OK，需 iOS 15.4 以上

- 建置：`vite.config.ts` 沒設 `build.target`，Vite 5 預設 `modules`（含 Safari 14），`package.json` 無 `browserslist`；`tsconfig.json` 目標 ES2022（只做型別，不補 polyfill）。
- 用到較新功能：`structuredClone`（`src/ui/store.ts:135-138`、`src/ui/carry.ts:51`）、CSS `:has()`（`src/styles/app.css:473,972`）、`100dvh`（`app.css:409`，有 `100vh` 備援）。這些在 Safari 15.4 起支援（我的既有知識，未查來源）。**iOS 15.4 以上不會因此壞；更舊的 iPhone 會壞。**
- 已 grep：`src/` 內沒有 `.at(`、`<dialog>`、`showModal`、`navigator.storage`、`localStorage`。
- 以上都**不是**目前打不開的原因（App 在沒有資料夾 API 時仍能載入並畫出畫面，已實測）。

### 3.6 版面（已實測首頁；其餘為程式推論）

- `index.html:9` 有 `viewport` meta；已實測 375px 寬首頁 `scrollWidth` ＝ 375，沒有橫向溢出。`public/manifest.webmanifest` 已有 `display: standalone`、`apple-touch-icon`，可加到主畫面。
- 表格有最小寬度（`app.css:401` 560px、`:904` 760px），靠容器橫向捲動；`docs/design/對稿-I-2a與I-3.md:44`（A-6）已記錄「375 寬步驟① 考科表的編輯／刪除鈕在畫面外，不捲看不到」。
- 專案已有手機版設計（`docs/design/DESIGN.md` 多處手機 375／390 規格、`docs/dispatch/完工-D-B.md:20` 375 驗過），設計稿主要面向桌機（`docs/design/DESIGN.md:410` 「沒驗到：真實手機」）。座位表編輯在手機上的實用性沒有測，也沒有專案決定。
- **沒有測**：點擊目標大小、iOS 輸入框放大（字級小於 16px 會自動放大）、安全區域、鍵盤遮擋。

### 3.7 瀏覽器儲存限制（如果改用瀏覽器儲存才要考慮）

- 目前 App **完全沒用** localStorage／sessionStorage（`src/ui/pages/Privacy.tsx:29` 隱私權頁也這樣寫），只用 IndexedDB 存資料夾控制代碼。
- 若改用 IndexedDB／OPFS 存資料：Safari 對「一般瀏覽、7 天沒互動」的網站會清除可由腳本寫入的儲存；**加到主畫面的網頁 App 有自己的計時，不在此限**（來源：WebKit Bugzilla 與報導，見第六節；來源多半為 2020–2022 年，現況需再確認）。另外無痕模式、使用者清除網站資料也會清空。**所以不能把瀏覽器儲存當唯一副本，必須搭配備份檔匯出。**

## 五、解法選項與建議

| # | 方案 | 成本 | 風險 | 要設計員？ | 影響排座引擎與資料？ |
|---|---|---|---|---|---|
| A | **維持 Chrome 電腦版限定**，但修掉 3.2 的誤導：不支援時整個拖曳區停用，提示改成明確的「iPhone／iPad 無法使用，請用電腦的 Chrome」 | 極小（半天內，改 `Init.tsx`＋測試） | 低 | 要（提示文案與停用樣式屬 UI） | 否 |
| B | **iPhone 唯讀檢視**：iPhone 上不排座、不編輯，只用 `<input type=file>` 匯入備份 .json 後查詢座位／考生（既有「考生查詢」） | 中（需新增「匯入整份備份」與一個唯讀模式，約 2–4 天） | 中：備份檔要從電腦傳到手機（AirDrop／iCloud） | 要 | 否（只讀） |
| C | **新增第二種儲存後端（OPFS 或 IndexedDB）＋備份匯出／匯入**，iPhone 可獨立使用全部功能 | 大（儲存層抽象已存在 `Repository` 介面 `src/ui/repository.ts:8-26`，要新實作並處理增量存檔、7 天清除、備份提醒；另要處理 PDF／多檔下載，約 1–2 週） | 高：資料只在瀏覽器、可能被清；手機編排座位的實用性未知；iOS 實機測試條件（我沒有 iPhone） | 要（手機版畫面、備份提醒） | 引擎不動；存檔層與 `Doc` 讀寫需動，需回歸 |
| D | **用 iPhone 當「顯示端」**：電腦匯出 PDF／xlsx 後傳到手機看（現在就能做，不改程式） | 0 | 無 | 否 | 否 |

### 我的建議：先做 A，同時請使用者決定 B／C 要不要做

- **先做 A**：成本最低、修正真實的誤導 bug、也讓老師一打開就知道原因，不會輸入半天才發現沒存。
- **使用者先回答：老師在 iPhone 上到底要做什麼？** 若只是「看座位表、查某個考生在哪間教室」→ 走 D（現在就能用）或 B；若是「在 iPhone 上完整排座」→ 才需要 C，而且要先確認小螢幕編輯是否可接受。
- **為什麼不直接選 C**：成本與風險最高；iOS 沒有檔案系統授權，資料只存瀏覽器內，與目前「資料在老師自己選的資料夾、可自己備份、可雲端同步」的承諾（隱私權頁）不同，需要重寫隱私權頁文字與備份流程；且我沒有 iPhone 無法在此驗收，需要使用者或測試員用實機驗。
- **為什麼 B 優於 C 作為中間方案**：只讀不會有資料遺失與衝突風險，引擎與存檔邏輯完全不動。

## 七、無法驗證的部分

1. 所有 iOS WebKit 的實際行為：檔案選擇器對 `.xlsx` 的過濾、下載管理員、多檔下載、`window.open` 彈出視窗、列印／存 PDF——**需要真實 iPhone**（建議：請使用者用 iPhone 開正式站，截圖初始畫面與試一次匯入名單；或交測試員）。
2. iOS 版本分佈（老師的 iPhone 是否 ≥ 15.4）。
3. 手機上點擊目標大小、輸入框自動放大、鍵盤遮擋等細部版面。
4. 現行 Safari 對儲存清除的最新政策。
5. 我沒有搜尋「iOS 對 `a[download]`、`structuredClone`、`:has()`、`dvh` 的支援版本」的官方來源，上述版本號為既有知識。
6. 實測模擬只改了 `showDirectoryPicker` 有無；沒有模擬 iOS 的其他引擎差異。
